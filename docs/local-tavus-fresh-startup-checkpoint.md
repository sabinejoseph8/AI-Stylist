# Fresh-process read-only checkpoint inspection

Continued authorized local preparation under the active goal on 16 October 2026. No spending, real credentials, provider requests or hosted changes are included.

## What startup can establish

The new disconnected startup inspector verifies signed authority reads, a separately signed database observation, a pinned trusted registry and a minimum known authority revision. It compares the complete logical state, projection and original operation marker to the registry entry for the current authority target. Another fresh authority read must show the same completed state after the database observation.

A successful result is deliberately diagnostic only:

```json
{
  "status": "checkpoint-consistent",
  "permissions": {
    "write": false,
    "reconcile": false,
    "sign": false,
    "resume": false
  },
  "reason": "fresh-owner-required"
}
```

Consistency does not reconstruct an original owner, signing handoff, token or consultation. The interface has read ports only. There is no bootstrap, advance, claim, reconcile, reapply or resume method, no default connection and no unsigned database-only fallback. The result is not an endpoint-readiness grant.

## Trust and refusal checks

The registry contains sanitized operation IDs, target metadata and projections. It does not contain original command arguments or receipt handoffs. Its digest and minimum revision are required trusted configuration, not learned from incoming checkpoint data. A correctly pinned but obsolete registry is held rather than automatically extended from a database snapshot.

Authority and database observation keys must differ. Proofs bind the store, policy, fresh nonce, key identity and expiry. Replies are copied before verification; a port cannot extend a signed proof's deadline by mutating an object during a later asynchronous read. The inspector also rejects non-JSON registry values, unexpected reader identities, malformed or forged evidence, expired proof, a lower revision, a pending operation and a changed final authority state. Unknown outcomes and cancellation remain held.

The missing-journal test removes the actual disposable authority ledger and verifies that a fresh client cannot reseed it. A missing trusted registry fails before authority work. No private key is generated by the startup inspector.

## Actual fresh process and PostgreSQL evidence

`cvi-startup-reader.ts` runs in a new Node process with public pins and registry summaries only. The original test authority/observer services retain their ephemeral private keys. The fresh process asks those ports for signed evidence through an isolated pipe and returns only the diagnostic result or a fixed held response. No private keys are copied into the client, chat, source checkpoint or Git.

The PostgreSQL rehearsal spawns a new inspector after each of the five committed transitions. It checks pending startup, missing/obsolete registry, unavailable authority, forged database signature and missing original handoff. Missing handoff still yields no sign or resume permission. Restoring only the database is refused. Restoring both old stores is also refused while the original parent retains the newer minimum revision.

The negative test deliberately loses that minimum along with coordinated rollback. A matching old checkpoint can then be diagnosed as consistent, while every permission remains false. This demonstrates why a production minimum floor must survive independently. It does not prove full application restart, independently administered services or recoverable production signing keys.
