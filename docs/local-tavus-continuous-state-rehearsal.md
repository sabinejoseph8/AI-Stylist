## One history across five transitions

The previous rehearsal tested each target in a separately prepared scenario. The new continuous mode keeps one PostgreSQL history and one authority journal through activation, domain commit, receipt claim, fencing and release. It preserves prior admissions, execution records, projections, receipts, grants and release tombstones between steps. Each step must commit, close and reconcile before the next phase can begin. A pending phase refuses the next request before admitting another authority operation.

The reference targets are generated by the actual existing validator and guarded SQLite adapter in a separate disposable reference model. The new authority is initialized once at that reference baseline; each trusted target is registered with its original hashed intent. No production authority is reset or seeded by a customer request. PostgreSQL then persists and reconciles the exact complete reference states in order.

The reference model provides an original transient receipt record when preparing the expected release target. This is a state persistence/reconciliation test, not the production application's original PostgreSQL signing handoff. It does not reconstruct that handoff from an observer snapshot, sign an application receipt or emit audio. Native application handoff and signing remain separate gates.

## Competing connection

During the domain transaction, a second PostgreSQL connection attempts the same operation and claim while the original connection holds the full-state lock. It is refused through lock timeout or original-transaction binding. The original transaction completes through its signed confirmation and reconciliation. No second execution row, new reservation or refunded claim is created. Ordinary runtime access to the reduced execution path remains revoked.

A separate authority test verifies that the next phase is refused while the prior operation is pending. That refusal does not spend the future operation's admission. These are participating-route concurrency checks, not universal fencing of every possible administrator or worker.

## Complete local checkpoint restores

The harness captures all six protected native tables: reduced state, admissions, full admissions, executions, releases and full state. After the sequence finishes, the disposable test administrator restores those tables in a transaction from the earlier checkpoint. It does not touch real customer data, production backups or permanent ledgers.

- Restoring only PostgreSQL is refused against the newer authority state.
- Restoring the newer PostgreSQL checkpoint again restores read-only consistency.
- Restoring only the authority journal is refused against the newer database.
- Negative boundary: restoring both database and authority to the same old checkpoint passes the current-state comparison. This preserves the need for independently protected restore floors; the test does not assert new signing permission or reapply an operation.

The read-only current-state check now requires the latest reconciled authority operation marker, as well as the complete aggregate and matching projection. A matching snapshot cannot substitute an unrelated operation marker. This check is not a cold-start authorization or a claim-reconstruction API.
